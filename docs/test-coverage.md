# Звіт про тестування та покриття коду (ЛР2)

Проєкт: Incident Recorder, плата NUCLEO-F411RE.

## 1. Що вимірювалось

Хостові тести (збираються `gcc` на комп'ютері, плата не потрібна) перевіряють логіку з `firmware/App/bringup.c`:
перетворення сирих даних у фізичні величини, обробку помилок шин, ідентифікацію чіпів,
послідовність команд SPI-flash і розбір UART-команд.

Покриття вимірювалось інструментом **gcov** (`gcc --coverage`) для файлу `firmware/App/bringup.c`.
Це єдиний на цей момент файл із логікою застосунку та драйверів сенсорів (окремих драйверів у `Devices/` ще немає).

## 2. Як відтворити

З кореня репозиторію (термінал Git Bash, потрібні `gcc`, `make`, `gcov`):

```
make test        # збірка й запуск тестів
make coverage    # те саме з вимірюванням покриття та перевіркою порогу
```

Параметри порогу задаються змінними `MIN_LINES` і `MIN_BRANCHES` у `tests/Makefile`
(за замовчуванням 80 і 70). Якщо покриття нижче, `make coverage` завершується з помилкою.
Вивід `printf` прошивки під час тестів зберігається в `tests/build/firmware_output.log`.

Детальний розбір за рядками (файл `bringup.c.gcov` з позначками виконаних і невиконаних рядків):

```
cd tests && gcov -b -o build build/test_bringup_cov-test_bringup.gcda
```

## 4. Поріг покриття і його обґрунтування

Поріг: **≥ 80 % рядків і ≥ 70 % гілок** (за метрикою «гілка взята хоча б один раз у кожному напрямку»).

- Для драйверів і прикладної логіки 80 % рядків є стандартним практичним мінімумом: вимагає покрити основні й помилкові шляхи, але не змушує писати тести заради цифри.
- Поріг гілок нижчий, бо частина гілок захищає від апаратних збоїв, які не можна відтворити без зміни коду або HAL (наприклад, вічний стан BUSY у `w25_wait_ready`).
- Поріг перевіряється автоматично скриптом `tests/coverage_gate.sh` у кожному pull request: падіння покриття нижче порогу робить CI червоним.
- Поточні значення (100 % і 86,25 %) перевищують поріг із запасом, тому він не підганяється під результат.

## 5. Що покрито (групи тестів)

| Група | Що перевіряється |
|---|---|
| Перетворення даних | `be16`; LSM303D (0,061 мг/LSB) і L3GD20H (8,75 мдпс/LSB), знак, усічення до нуля; приклад розрахунку BMP180 з datasheet (T = 15,0 °C, P = 69964 Па) |
| Помилки шин | збій читання, NACK пристрою, збій окремих транзакцій BMP180; вихідні значення не псуються при помилці; CS у SPI завжди відпускається |
| Ідентифікація | WHO_AM_I / chip ID / JEDEC / PID+VER камери: правильні значення і помилкові ID |
| Послідовність SPI-flash | WREN перед кожним стиранням і записом, адреса `0x7FF000`, опитування BUSY, порівняння записаного і прочитаного, фіксація записів без WREN |
| UART-команди | echo, невідома команда, переповнення буфера, команди `id`, `i2c`, `data`, `spi`, `flash`, `sccb`, `uart`, `help`, порожній рядок, ініціалізація |
| Реальні вектори з логічного аналізатора | BMP180 (22 байти калібрування, UT = 0x54BB, UP = 0x9FD6 → 23,7 °C, 99817 Па); LSM303D (6 байтів двох записів); 16 байтів flash із запису 04; JEDEC `EF 40 17`; UART `Hello!` (11 байтів) |

Test doubles (`tests/fakes/fake_bus.c`): fake I²C (регістрова модель LSM303D, L3GD20H, BMP180), fake SPI (модель W25Q64: JEDEC, WREN/WEL, стирання, запис, читання, BUSY), fake SCCB, fake UART. Журнал транзакцій дозволяє перевіряти не лише результат, а й послідовність викликів (поведінка mock).

Очікувані числа для реальних векторів обчислені окремим розрахунком за формулами Bosch, а не взяті з виводу прошивки.

## 6. Знайдені дефекти та спостереження

| № | Симптом (виявлено тестом) | Причина | Статус |
|---|---|---|---|
| 1 | `bmp180_read` повертає `BUS_OK`, хоча запис команди вимірювання (0x2E / 0x34) завершився помилкою | результат `g_i2c_platform_bus.write` не перевіряється | не виправлено, тест позначено `KNOWN_DEFECT` |
| 2 | `selftest_lsm303d` не дає FAIL, якщо запис CTRL1/CTRL2 не вдався | результати записів не перевіряються | не виправлено, `KNOWN_DEFECT` |
| 3 | Дані акселерометра із записів 01 і 02: модуль ≈ 2,26 g замість ≈ 1 g (вісь Y = `0x7FF8`) | арифметика прошивки правильна; потрібна перевірка стенда (орієнтація, вісь Y) | передано апаратній частині, `KNOWN_DEFECT` |
| 4 | Розбіжність у B5 BMP180: 2400 у коді, 2399 у прикладі datasheet | у C ділення від'ємних чисел усікається до нуля; T і P збігаються з очікуваними | задокументовано, тест допускає 2399/2400 |

Знайдено при читанні коду, тестами не підтверджено: `w25_wait_ready` не має обмеження за часом (вічне очікування при застряглому BUSY); ділення на нуль у `bmp180_calc_temp`, якщо `x1 + md == 0`; `bus_status_t` не розрізняє NACK і timeout.

## 7. Що свідомо не покрито

- `firmware/Platform/bus_adapters.c` — прямі виклики HAL і ручне керування GPIO для SCCB. Перевіряється лише на залозі й логічним аналізатором (у тому числі STOP між записом субадреси і читанням).
- `firmware/Core/` (`main.c`, ініціалізація периферії від CubeMX) і HAL/CMSIS — вендорський і згенерований код.
- Таймінги (частоти SCL/SCK, затримки): на хості `platform_delay_ms` порожня, реальні часи вимірюються на логічному аналізаторі.
- Фізична правдоподібність даних (1 g, кімнатна температура): перевіряється на стенді; тести перевіряють лише арифметику.
- Не відтворюються збої, що потребують зміни коду (вічний BUSY, нульове калібрування BMP180).

## 8. Обмеження методу

Тест підключає `bringup.c` напряму через `#include`, щоб бачити `static`-функції без зміни прошивки. Після винесення драйверів у `Devices/` тести слід перевести на підключення заголовків, а покриття вимірювати для окремих модулів драйверів і прикладної логіки.
Власний мінімальний фреймворк (`tests/minitest.h`) замість Unity не дає автоматичних mock-ів (CMock), розширеного порівняння типів і готових звітів; замість цього перевірка послідовності транзакцій виконується через журнал fake-шин.
