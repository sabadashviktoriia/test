### 4.2 Ідентифікація чипа

Даташит описує серію **W25Q64JV** загалом. Фактичний чип на платі промарковано як **`W25Q64JVSIQ 2309`**.

### 4.3 Інтерфейс — SPI2

* Підтримує **Mode 0** (CPOL=0, CPHA=0) і **Mode 3** (CPOL=1, CPHA=1) \[DS, розд. 6.1, с.11]. Обрано Mode 0 (типове значення CubeMX за замовчуванням).
* Максимальна частота CLK: **133 МГц** (VCC 3.0–3.6В) / **104 МГц** (2.7–3.0В) для більшості інструкцій; для **Read Data (03h)** ліміт — **50 МГц** \[DS, розд. 9.6, с.63]. SPI2 на STM32F411 (APB1, макс. \~50 МГц) не буде вузьким місцем.
* Використовується лише Standard SPI (без Dual/Quad) — `/WP` і `/HOLD` лишаються звичайними дискретними пінами, а не IO2/IO3.

## 5\. OV7670 — камера VGA (Software SCCB + паралельна шина)

### 5.1 Ідентифікація breakout‑модуля

За фотографією нашого конкретного модуля:

* **18‑pin OV7670 breakout module**.
* На зворотній стороні модуля стоять два лінійні стабілізатори (LDO) з маркуванням:

  * **`65X5`** → за правилом маркування Torex XC6206 (позиція 2 = "5" — діапазон 0.1–3.0В, позиція 3 = "X" — 2.8В) → **XC6206P282, вихід 2.8 В**.
  * **`65K5`** → позиція 3 = "K" — 1.8В → **XC6206P182, вихід 1.8 В**.

Отже: **breakout містить onboard LDO, які самостійно формують внутрішні домени 2.8В (аналог) та 1.8В (цифрове ядро) з єдиної зовнішньої напруги живлення.**

|Цифрове ядро|DVDD|1.8 В ±10%|DS, с.1|

### 5.3 Критичне застереження щодо рівнів логіки

Не можна стверджувати, що OV7670 повністю сумісний з 3.3В логікою "з коробки": сам сенсор (за DS, Табл.3, с.5) має **DOVDD (I/O) в діапазоні 1.7–3.0 В**, тобто офіційна робоча напруга I/O не перевищує 3.0В, тоді як Nucleo видає 3.3В.

Оскільки в списку обладнання нашої команди окремого level‑shifter не зазначено, це фіксується як **апаратний ризик**: живлення модуля від 3.3В працює для більшості таких breakout‑плат на практиці (абсолютний максимум VDD‑IO — 4.5В, DS Табл.2, с.5, тобто пошкодження малоймовірне), але відповідність сигнальних рівнів OV7670 конкретно на нашому 3.3В‑логічному STM32 **не підтверджена офіційним даташитом сенсора** і має розглядатись як припущення, що потребує практичної перевірки (напр. осцилографом на DOUT лінії).

### 5.4 Інтерфейс — SCCB (I²C‑сумісний), реалізація — software

* Керування регістрами — через **SCCB**, сумісний з I²C \[DS, General Description, с.1].
* 7‑бітна адреса: **`0x21`** (з інструкцій `0x42` запис / `0x43` читання) \[DS, розд. "Register Set", с.11].
* Максимальна частота SCCB clock: **400 кГц** \[DS, Табл.4, с.6].

**Чому SCCB винесено на окремі піни (PA0/PA1), а не на спільну шину I2C1 (PB8/PB9) з MPU‑6050:**

1. Адреси не конфліктують (MPU‑6050 = `0x68`, OV7670 = `0x21`) — це не є проблемою.
2. Проблема потенційно в **рівнях логіки та підтягувальних резисторах**: I2C1 (PB8/PB9) вже підтягнутий під 3.3В‑домен MPU‑6050/Nucleo, а I/O камери офіційно розрахований максимум на 3.0В (розд. 5.3). Змішувати два пристрої з різними допустимими рівнями на одній апаратній I²C‑шині без окремої перевірки — зайвий ризик.
3. SCCB не завжди строго відповідає I²C‑протоколу (можлива відсутність ACK у деяких транзакціях) — апаратний периферійний блок I2C1 STM32 може конфліктувати з такою поведінкою, тоді як software (bit‑banged) реалізація на вільних пінах **PA0/PA1** дає гнучкість під час налагодження.
4. **PB8/PB9 у будь‑якому разі зайняті** апаратним I2C1 у `firmware.ioc` під MPU‑6050 (розд. 1) — цей пункт фіксує рішення, а не є додатковим аргументом "проти" (шина була б фізично доступна для розділення в часі, але з урахуванням п.2–3 обрано окремі піни).

**Наслідок для прошивки:** SCCB на PA0/PA1 реалізується програмно (bit‑bang).

### 5.6 Обґрунтування вибору пінів

1. PB8/PB9 лишаються виключно за I2C1 (MPU‑6050).
2. PB12–PB15 лишаються за SPI2 (W25Q64JV).
3. PA2/PA3 лишаються за USART2 (printf/monitor).
4. PB3 не використовується — зайнятий SWO у поточному `firmware.ioc`.
5. PA10 не віддається камері — лишається за MPU‑6050 INT (розд. 3.3).
6. PA13/PA14 не чіпаються — SWD (ST‑LINK debug).
7. D0–D7 розміщені на одному порту GPIOC (PC2–PC9) — зручно для читання 8‑бітної шини одним зчитуванням регістра порту.
8. VSYNC/HREF/PCLK — на PC10/PC11/PC12, вільні Morpho‑піни, що не конфліктують з LSE (PC14/PC15) чи User Button (PC13).
9. XCLK — на PA8 (підтримує функцію MCO1 для генерації тактового сигналу).
10. SCCB винесено на PA0/PA1 як software‑реалізація (обґрунтування — розд. 5.4).

## 6\. Ризики та застереження

1. **STM32F411 не має апаратного DCMI.** DCMI на STM32F4 з'явився лише у моделях F407/F417 і вище; F401/F410/F411 ("value line") цього блоку не мають. **Наслідок:** D0–D7, PCLK, HREF, VSYNC підключені як звичайні GPIO (розд. 5.5); захват кадру реалізується програмно у firmware. Це апаратне обмеження, зафіксоване тут.
2. **Рівні логіки I/O OV7670 (розд. 5.3).** Breakout приймає 3.3В живлення, але сам сенсор офіційно розрахований на DOVDD максимум 3.0В.
3. **`/WP` і `/HOLD` W25Q64JV** мають бути на логічній HIGH (розд. 4.4), інакше можливі непередбачувані зависання SPI‑транзакцій.
4. **MPU‑6050 стартує в режимі SLEEP** (`PWR_MGMT_1` = 0x40 за замовчуванням, розд. 3.4) — прошивка повинна явно скинути цей біт.
5. **Software SCCB для камери (розд. 5.4)** — вимагає бітбенгінг-реалізації I²C‑подібного протоколу на GPIO (PA0/PA1) у прошивці; узгоджено окремо від апаратного I2C1, щоб уникнути змішування різних допустимих рівнів логіки на одній шині.
