# Pinout та схема підключення

## 1. Апаратна конфігурація

Стенд побудовано на платі **STM32 NUCLEO-F411RE** та чотирьох зовнішніх модулях, визначених у PRD:

| Пристрій                               | Призначення                                                 | Інтерфейс                      |
| -------------------------------------- | ----------------------------------------------------------- | ------------------------------ |
| **STM32 NUCLEO-F411RE**                | основний мікроконтролер і керування стендом                 | GPIO, I²C, SPI, UART, TIM, DMA |
| **GY-89 (LSM303D / L3GD20H / BMP180)** | акселерометр, гіроскоп, магнітометр, барометр і температура | I²C                            |
| **OV7670**                             | фотографування середовища при виявленні інциденту           | DVP + SCCB                     |
| **W25Q64**                             | енергонезалежне зберігання журналу та кадрів                | SPI                            |
| **YP-05 на FT232RL**                   | командний інтерфейс із ПК                                   | UART <-> USB                   |

Підключення виконується **без пайки**, із використанням готових модулів та штатних роз'ємів NUCLEO-F411RE. Усі зовнішні пристрої підключаються одночасно в одній прошивці.

Для STM32 прийнято clock tree з `SYSCLK = 100 MHz`, `HCLK = 100 MHz`, `PCLK1 = 50 MHz` і `PCLK2 = 100 MHz`. Таймери, тактовані від APB1 та APB2, працюють від `100 MHz`. Детальний розрахунок параметрів периферійних шин наведено в розділі 5.

### 1.1. Прийняті принципи розкладки

1. **GY-89** підключено до апаратного `I2C1` на `PB8/PB9`. Це штатні alternate functions `I2C1_SCL/I2C1_SDA` для STM32F411. На NUCLEO-F411RE ці піни виведені на ST Morpho та відповідають Arduino `D15/D14`. [[DS10314, Table 9](https://www.st.com/resource/en/datasheet/stm32f411rc.pdf); [UM1724, Tables 16, 29](https://www.st.com/resource/en/user_manual/DM00105823-.pdf)]

2. GY-89 використовується у базовій конфігурації готового модуля для роботи з I²C. Виводи `SD0/SA0`, `CS1` та `CS2` **не підключаються зовнішніми проводами** і не змінюються програмно або через зовнішню перемичку. Завдяки цьому адресна конфігурація модуля не залежить від додаткового монтажу. Фактичні адреси та ідентифікатори вузлів GY-89 будуть зафіксовані в розділі 3. [[документація GY-89](https://www.beemong.com/product/gy-89-10dof-lsm303dl3gd20-bmp180-sensor-module); [LSM9DS0](https://www.st.com/resource/en/datasheet/lsm9ds0.pdf)/[L3GD20H datasheet](https://www.st.com/resource/en/datasheet/l3gd20h.pdf)]

3. **W25Q64** підключено до апаратного `SPI2` на `PB13/PB14/PB15`, а `CS#` реалізовано окремим GPIO `PB12`. Така розкладка не використовує `SPI1` на `PA5/PA6/PA7`, зокрема `PA5`, який штатно підключений до user LED Nucleo. [[DS10314, Table 9](https://www.st.com/resource/en/datasheet/stm32f411rc.pdf); [UM1724, Tables 16, 29](https://www.st.com/resource/en/user_manual/DM00105823-.pdf)]

4. **YP-05** використовує `USART1` на `PA9/PA10`. `USART2` на `PA2/PA3` залишається за штатним ST-LINK VCP Nucleo і використовується для стандартного `monitor`. [[DS10314, Table 9](https://www.st.com/resource/en/datasheet/stm32f411rc.pdf); [UM1724, §7.10](https://www.st.com/resource/en/user_manual/DM00105823-.pdf)]

5. **OV7670** не використовує DCMI, оскільки STM32F411RE не має периферії DCMI. Паралельний DVP-інтерфейс камери захоплюється через GPIO. Усі вісім ліній даних підключені до `GPIOC`; `PC9` між `D6` та `D7` виділено під `PCLK` через `TIM3_CH4`. [[DS10314, Table 9](https://www.st.com/resource/en/datasheet/stm32f411rc.pdf)]

6. `PCLK` камери використовується як джерело DMA-запитів через `TIM3_CH4`. DMA не потребує окремого периферійного входу для кожного біта `D0...D7`: джерелом кожного трансферу є регістр `GPIOC->IDR`, який містить одночасні логічні рівні всіх ліній порту. Після DMA-трансферу програмне забезпечення виділяє біти `PC2...PC8` та `PC10`, що відповідають `D0...D7`. [[RM0383, §9.3](https://www.st.com/resource/en/reference_manual/dm00119316.pdf); [RM0383, Table 27](https://www.st.com/resource/en/reference_manual/dm00119316.pdf)]

7. Керування `OV7670 XCLK` виконується через `PA8/TIM1_CH1`, що дозволяє генерувати тактовий сигнал камери апаратним таймером. [[DS10314, Table 9](https://www.st.com/resource/en/datasheet/stm32f411rc.pdf)]

8. Керування `OV7670 SCCB` винесено на окрему пару GPIO `PB6/PB7`. Це дозволяє не займати `I2C1`, який використовується GY-89. `RET` та `PWDN` керуються окремими GPIO `PA0` та `PA1`. [[DS10314, Table 9](https://www.st.com/resource/en/datasheet/stm32f411rc.pdf); [OV7670 datasheet](https://www.olimex.com/Products/Components/Camera/CAMERA-OV7670/resources/OV7670.pdf)]

9. Ресурси Nucleo **LD2 (PA5)**, **USER button B1 (PC13)**, **SWD (PA13/PA14)** та **ST-LINK VCP (PA2/PA3)** не використовуються зовнішніми модулями і залишаються доступними за штатним призначенням. [[UM1724, §7.6–7.7, §7.10](https://www.st.com/resource/en/user_manual/DM00105823-.pdf)].

10. Для живлення використовується `+5V` та `+3V3` Nucleo. GY-89 живиться через `VIN = +5V`. OV7670 та W25Q64 живляться від `+3V3`. YP-05 живиться через USB Type-C від ПК та має працювати з UART-логікою `3,3 В`.

11. Для запропонованої розкладки **зміна типової конфігурації solder bridges NUCLEO-F411RE не потрібна**. Підключення виконується безпосередньо через штатні роз'єми `CN7` та `CN10`. [[UM1724, Tables 16, 29](https://www.st.com/resource/en/user_manual/DM00105823-.pdf)]

### 2.1. Перевірка OV7670 щодо DMA та конфліктів периферії

Для захоплення DVP використовується така внутрішня схема:

```text
OV7670 PCLK
     │
     ▼
PC9 / TIM3_CH4
     │
     │ DMA request
     ▼
DMA1 / Channel 5 / Stream 2
     │
     │ peripheral-to-memory
     ▼
GPIOC->IDR ───────────────► frame buffer
     │
     ├── PC2  -> D0
     ├── PC3  -> D1
     ├── PC4  -> D2
     ├── PC5  -> D3
     ├── PC6  -> D4
     ├── PC7  -> D5
     ├── PC8  -> D6
     └── PC10 -> D7
```

Така схема **не потребує окремого DMA request для кожного DVP data bit**. `TIM3_CH4` формує запит на DMA, після чого DMA зчитує значення всього `GPIOC->IDR`. Тому той факт, що `D7` знаходиться на `PC10`, а не на `PC9`, не є проблемою.

`PC9` використовується у режимі Alternate Function `TIM3_CH4`, а `PC2–PC8`, `PC10`, `PC11` та `PC12` — у режимі GPIO. Це не створює timer conflict: `TIM3_CH2` та `TIM3_CH3`, доступні на `PC7` і `PC8`, у цій схемі навмисно не активуються.

У вибраній конфігурації `TIM3` використовується лише каналом `CH4` для camera PCLK, тому спільний timer prescaler не створює конфлікту з іншими функціями. `TIM1_CH1` на `PA8` використовується окремо для XCLK.

DMA mapping для `TIM3_CH4` визначений у **RM0383 Table 27**. Він не збігається з DMA request, який буде використовуватися для запланованого `SPI2` та `I2C1`, тому розкладка не створює конфлікту одного DMA stream/channel з іншою периферією [RM0383, Table 27].

Важливо, що DMA-захоплення `GPIOC->IDR` є саме механізмом реалізації DVP на STM32F411, а не штатним camera peripheral. Тому максимальна досяжна частота захоплення визначатиметься не лише можливістю DMA, а й часовими параметрами камери, частотою `PCLK`, налаштуваннями DMA та пропускною здатністю AHB. Ці параметри будуть зафіксовані й розраховані в розділі 5 та перевірені логічним аналізатором відповідно до вимог технічного завдання.

## 3. Адреси та ідентифікатори

У цьому розділі зафіксовано адреси та ідентифікаційні значення, які повинна отримувати прошивка STM32 під час початкової перевірки підключених пристроїв. Адреси визначено з урахуванням фактичної розкладки пінів, станів адресних входів і вибору інтерфейсу на модулях.

Для I²C розрізняються **7-бітна адреса пристрою** та **8-бітний байт адреси на шині**, який додатково містить біт напрямку `R/W`. Для SCCB наведено як 7-бітне представлення адреси, так і байти, визначені документацією виробника камери. Для SPI Flash замість адреси пристрою використовується команда читання ідентифікації.

### 3.1. GY-89: I²C-адреси та регістри ідентифікації

Для цього проєкту зафіксовано склад модуля GY-89: **LSM303D + L3GD20H + BMP180**. Усі три мікросхеми підключені до спільної апаратної шини `I2C1` (`PB8/SCL`, `PB9/SDA`), але мають різні адреси.

Відповідно до прийнятої конфігурації модуля, виводи `CS1` (LSM303D) і `CS2` (L3GD20H) залишаються непідключеними зовнішніми проводами та утримуються на рівні `High` наявними на модулі підтяжками. Вивід `SD0/SA0` також залишається без зовнішнього підключення та утримується на рівні `High` внутрішньою підтяжкою модуля.

За таких умов LSM303D та L3GD20H працюють через I²C і використовують адресні варіанти, вибрані станом `SA0 = High`. BMP180 має фіксовану адресу I²C.

#### 3.1.1. Врахування формату адрес у STM32 HAL

У таблиці вище основними ідентифікаторами пристроїв є **7-бітні адреси**. Саме їх потрібно зберігати у конфігурації драйверів:

```c
#define LSM303D_ADDR_7BIT  0x1D
#define L3GD20H_ADDR_7BIT  0x6B
#define BMP180_ADDR_7BIT   0x77
```

У стандартних функціях STM32F4 HAL для I²C параметр `DevAddress` передається у зсунутому вигляді — `addr7 << 1`. Наприклад, для LSM303D використовується `0x1D << 1`, тобто `0x3A`. Напрямок передачі задається функцією читання або запису; до параметра `DevAddress` не потрібно додатково додавати біт читання.

Адреса регістра, наприклад `0x0F` для `WHO_AM_I`, є окремим параметром і не повинна зсуватися разом з адресою пристрою.

Для початкової перевірки прошивка повинна звернутися до всіх трьох адрес і порівняти прочитані значення ID з таблицею. Самої наявності ACK від пристрою недостатньо для підтвердження його правильної ідентифікації.

#### 3.2.1. Початкова послідовність ідентифікації

Перед читанням ідентифікаторів потрібно виконати програмне скидання регістрів камери відповідно до рекомендацій OmniVision:

1. Переконатися, що камера вийшла із зовнішнього стану скидання, а на `XCLK` подається тактовий сигнал.
2. Через SCCB записати `0x80` у регістр `COM7` (`0x12`), використовуючи адресу запису `0x42`.
3. Почекати щонайменше `1 ms`, як зазначено в Implementation Guide.
4. Прочитати `PID` (`0x0A`) та `VER` (`0x0B`) і порівняти їх з очікуваними значеннями `0x76` та `0x73` відповідно.

Джерело послідовності скидання: [OV7670 Implementation Guide, §8.1.1, p. 44](https://www.haoyuelectronics.com/Attachment/OV7670%20%2B%20AL422B%28FIFO%29%20Camera%20Module%28V2.0%29/OV7670%20Implementation%20Guide%20%28V1.0%29.pdf).

Оскільки використовується саме SCCB, читання необхідно реалізувати та аналізувати відповідно до протоколу камери. Під час перевірки логічним аналізатором окремо слід зафіксувати поведінку `SDA` у фазі, де стандартний I²C-декодер очікує ACK, і зіставити її з фактичною послідовністю SCCB.

Адреса `0x21` не конфліктує з адресами GY-89. Крім того, камера підключена до окремої фізичної пари GPIO, тому між SCCB та апаратним `I2C1` немає спільних сигнальних ліній.

#### Процедура перевірки

Для ідентифікації пам'яті прошивка повинна виконати таку послідовність:

1. Перевести `CS#` (`PB12`) у низький рівень.
2. Передати команду `0x9F`.
3. Прочитати три байти відповіді: `0xEF`, `0x40`, `0x17`.
4. Перевести `CS#` у високий рівень після завершення транзакції.

Отримані байти перевіряються в такому порядку: `Manufacturer ID = 0xEF`, `Memory Type ID = 0x40`, `Capacity ID = 0x17`. Усі три байти повинні бути прочитані в межах однієї транзакції, поки `CS#` залишається активним.

Не слід плутати команду `0x9F` з командою `0x90` (`Read Manufacturer/Device ID`): для W25Q64FV остання повертає інший формат ідентифікатора пристрою. У цьому проєкті основним тестом є саме `0x9F`, оскільки він дозволяє перевірити повний JEDEC ID і відповідність очікуваній пам'яті.

YP-05 не має адреси на I²C або SPI і не ідентифікується через регістри `WHO_AM_I` чи JEDEC ID. Це USB-UART міст, робота якого перевіряється окремо через UART-командний інтерфейс і відповідь прошивки.

## 4. Бюджет живлення

Це гранична характеристика регулятора, а не гарантований вільний струм для зовнішніх модулів: частину ресурсу використовує сама плата [[UM1724, §7.5.4, p. 23](https://www.st.com/resource/en/user_manual/dm00105823.pdf)].

GY-89 живиться через `VIN = +5V`, відповідно до специфікації готового модуля, у якій заявлені живлення 5 В і вбудований перетворювач логічних рівнів. Мікросхеми LSM303D та L3GD20H самостійно не розраховані на живлення 5 В; сумісність забезпечується саме обв'язкою готового модуля [[опис модуля GY-89](https://arduino.ua/prod2575-modyl-gy-89-kombinovanih-10-dof-datchikiv-l3gd20h-lsm9ds0-bmp180), [LSM303D datasheet, Table 5, p. 12](https://www.st.com/resource/en/datasheet/lsm303d.pdf), [L3GD20H datasheet, Table 4, p. 11](https://www.pololu.com/file/0J731/L3GD20H.pdf)].

### 4.3. Бюджет лінії `+3V3` NUCLEO-F411RE

Від лінії `+3V3` Nucleo живляться лише два зовнішні модулі: OV7670 і W25Q64. GY-89 використовує окрему лінію `+5V`, а YP-05 — живлення від USB Type-C ПК.

Для перевірки запасу регулятора U4 застосовано консервативний бюджет: для камери використано проєктний резерв 30 мА, а для SPI Flash — максимальний струм 25 мА під час програмування або стирання.

| Навантаження лінії `+3V3`                                                  | Розрахунковий струм |
| -------------------------------------------------------------------------- | ------------------: |
| OV7670, проєктний резерв                                                   |               30 мА |
| W25Q64FV, піковий струм програмування/стирання                             |               25 мА |
| **Сумарний проєктний бюджет зовнішніх навантажень**                        |           **55 мА** |
| Максимальна струмова здатність регулятора U4 за UM1724                     |              500 мА |
| **Арифметичний запас регулятора до врахування власних навантажень Nucleo** |          **445 мА** |

Розрахунок:

$$
I_{\text{external}} = 30 + 25 = 55\ \text{мА}
$$

$$
I_{\text{gross margin}} = 500 - 55 = 445\ \text{мА}
$$

Отже, зовнішні модулі потребують проєктного бюджету 55 мА, що становить 11 % від зазначеної в UM1724 максимальної струмової здатності регулятора U4.

**Запас 445 мА не є гарантованим вільним струмом на роз'ємі Nucleo.** Це арифметична різниця до врахування споживання самого мікроконтролера, бортового світлодіода, інших споживачів лінії 3,3 В та температурних обмежень регулятора.

Повний бюджет визначається формулою:

$$
I_{\text{margin}} =
500\ \text{мА}
-I_{\text{Nucleo internal}}
-55\ \text{мА}
$$

Для орієнтовної верхньої оцінки можна врахувати також паспортний струм STM32F411RE: до 34,7 мА за граничними умовами Table 24 даташита [DS10314, Table 24, p. 72](https://www.st.com/resource/en/datasheet/stm32f411ce.pdf). Проте цей розрахунок не охоплює всіх бортових компонентів плати, тому остаточний запас потрібно підтвердити вимірюванням.

### 4.4. Перевірка загального живлення від USB

Згідно з [UM1724, §7.5.1, Table 6, p. 21](https://www.st.com/resource/en/user_manual/dm00105823.pdf), обмеження струму для NUCLEO-F411RE при живленні через USB CN1 залежить від положення JP1:

| Конфігурація JP1                   | Допустимий струм для плати та розширень |
| ---------------------------------- | --------------------------------------: |
| JP1 — перемичку знято (`OFF`)      |                               До 300 мА |
| JP1 — перемичку встановлено (`ON`) |                               До 100 мА |

Для цього стенда приймається конфігурація **JP1 = OFF**, що відповідає ліміту 300 мА. Фактичне положення JP1 необхідно перевірити на платі перед першим запуском.

Для попередньої оцінки струмового навантаження USB приймається такий бюджет зовнішніх модулів:

| Навантаження                                                      | Проєктний бюджет |
| ----------------------------------------------------------------- | ---------------: |
| OV7670 та W25Q64 через `+3V3`                                     |            55 мА |
| GY-89 через `+5V`                                                 |            25 мА |
| **Сумарний попередній бюджет зовнішніх модулів**                  |        **80 мА** |
| Граничний струм USB для Nucleo та розширень                       |           300 мА |
| **Залишок до граничного значення для бортових споживачів Nucleo** |       **220 мА** |

Залишок 220 мА є попередньою оцінкою, а не виміряним запасом. У ній використано закладені проєктні навантаження, а струм, який споживають бортові компоненти Nucleo, ще потрібно підтвердити на практиці. Під час остаточної перевірки вимірюється сумарний струм стенда від USB за одночасної роботи всіх модулів.

Якщо фактичний струм плати разом із розширеннями перевищує 300 мА, UM1724 вимагає живити Nucleo через зовнішнє джерело, підключене до `E5V` або `VIN`, дотримуючись послідовності підключення з §7.5.2, pp. 22–23. Зміна джерела живлення повинна бути зафіксована в документації та не повинна призводити до одночасного неконтрольованого живлення однієї шини від двох джерел.

YP-05 у цьому розрахунку не включений до струму живлення Nucleo, оскільки він живиться через окремий USB-кабель. При цьому споживання адаптера все одно враховується під час оцінювання загального навантаження відповідного USB-порту ПК.

### 4.5. Обґрунтування окремого джерела живлення

У поточному складі стенда немає сервоприводів, двигунів або інших силових виконавчих механізмів, для яких потрібно передбачати окреме джерело живлення. OV7670 є сенсорним пристроєм, а W25Q64 — пристроєм збереження даних.

Для наявних модулів прийнято таке рішення:

* **GY-89** живиться через `+5V` Nucleo, оскільки готовий модуль заявлений для живлення 5 В і має вбудоване узгодження рівнів.
* **OV7670** живиться через `+3V3`, оскільки саме таке живлення передбачене для використаного готового модуля.
* **W25Q64** живиться через `+3V3`, що відповідає діапазону 2,7–3,6 В для мікросхеми W25Q64FV [[datasheet, §7.2 та Table 7.4, p. 73](https://www.pjrc.com/store/w25q64fv.pdf)].
* **YP-05** живиться через USB Type-C від ПК, без підключення його `VCC` до живлення Nucleo.

Для цього набору компонентів окреме силове джерело не є обов'язковим за умови, що фактичне споживання стенда відповідає наведеному бюджету.

### 4.6. Перевірка бюджету живлення після монтажу

До початку тривалих випробувань потрібно підтвердити розрахунковий бюджет на реальному обладнанні.

1. Виміряти струм, який споживає готовий модуль GY-89 від `+5V` у штатному режимі моніторингу.
2. Виміряти струм лінії `+3V3` із підключеними OV7670 та W25Q64. Перевірити навантаження під час захоплення кадру та одночасного запису даних у Flash.
3. Виміряти сумарний струм NUCLEO-F411RE від USB при одночасно підключених модулях та активній прошивці.
4. Переконатися, що напруга `+3V3` залишається в допустимому діапазоні та що перезапуск камери, операції стирання/запису Flash і робота UART не супроводжуються перезапуском мікроконтролера.

## 5. Параметри шин і тактування

У цьому розділі визначено робочі частоти периферійних інтерфейсів, режими передавання даних та параметри дільників STM32F411RE. Усі розрахунки виконано на основі прийнятого clock tree з `SYSCLK = 100 MHz`, `HCLK = 100 MHz`, `PCLK1 = 50 MHz` і `PCLK2 = 100 MHz`.

### 5.1. Прийняте дерево тактування

Для всіх розрахунків використовуються такі частоти шин і таймерів:

| Вузол clock tree | Конфігурація | Розрахункова частота | Призначення                       |
| ---------------- | ------------ | -------------------: | --------------------------------- |
| Джерело `SYSCLK` | `PLLCLK`     |              100 MHz | Системне тактування               |
| `SYSCLK`         | —            |              100 MHz | Системна частота STM32            |
| AHB prescaler    | `/1`         |                    — | Без поділу частоти системної шини |
| `HCLK`           | `SYSCLK / 1` |              100 MHz | Cortex-M4, AHB, DMA, GPIO         |
| APB1 prescaler   | `/2`         |                    — | Дільник периферійної шини APB1    |
| `PCLK1`          | `HCLK / 2`   |               50 MHz | `I2C1`, `SPI2`, `USART2`, `TIM3`  |
| Таймери APB1     | `2 × PCLK1`  |              100 MHz | `TIM3` та інші таймери APB1       |
| APB2 prescaler   | `/1`         |                    — | Без поділу частоти APB2           |
| `PCLK2`          | `HCLK / 1`   |              100 MHz | `USART1`, `TIM1`                  |
| Таймери APB2     | `PCLK2`      |              100 MHz | `TIM1` та інші таймери APB2       |

Частоти узгоджуються з обмеженнями STM32F411: APB1 працює не вище 50 MHz, APB2 — до 100 MHz, а таймери можуть отримувати тактування до 100 MHz. [[STM32F411 datasheet, Table 4, p. 28; Figure 3, p. 16](https://www.st.com/resource/en/datasheet/stm32f411re.pdf)].

### 5.2. I²C1 — сенсорний модуль GY-89

GY-89 підключено до апаратного `I2C1` через `PB8/SCL` і `PB9/SDA`. Шина обслуговує три вузли: LSM303D, L3GD20H і BMP180 з адресами, визначеними в підрозділі 3.1.

Для початкової інтеграції вибрано **Standard-mode, 100 kHz**. Це консервативний режим, достатній для читання ID-регістрів, конфігурації сенсорів та отримання вимірювань. Перехід у Fast-mode не потрібний для первинної перевірки й може бути розглянутий пізніше після підтвердження якості фронтів та підтяжок шини.

| Параметр                     | Значення             |
| ---------------------------- | -------------------- |
| Периферія                    | `I2C1`               |
| Піни                         | `PB8/SCL`, `PB9/SDA` |
| Alternate Function           | `AF4`                |
| Джерело тактування периферії | `PCLK1 = 50 MHz`     |
| Режим                        | Standard-mode        |
| Цільова частота `SCL`        | 100 kHz              |

#### 5.2.1. Розрахунок частоти

Конфігурація `CCR = 250`, `TRISE = 51`, `FREQ = 50 MHz` забезпечує номінальну частоту `SCL = 100 kHz` за заданої частоти `PCLK1`.

Формули та правила програмування регістрів наведені в [RM0383, §18.6.2, §18.6.8, p. 499, §18.6.9, p. 500](https://www.st.com/resource/en/reference_manual/dm00119316.pdf).

Лінії `SCL` і `SDA` повинні працювати у режимі open-drain із зовнішніми підтяжками. Внутрішні підтяжки GPIO STM32 не використовуються як основні резистори шини. Перед переходом до Fast-mode необхідно перевірити фактичні рівні HIGH, час наростання та відсутність надмірних паралельних підтяжок на готовому модулі GY-89.

Для логічного аналізатора потрібно зафіксувати звернення до кожного вузла, читання відповідного ID-регістра та хоча б одне багатобайтове читання даних. Номінальна частота за розрахунком — 100 kHz; фактичну частоту слід виміряти в PulseView.

### 5.3. SCCB — керування камерою OV7670

Керування OV7670 реалізовано програмно через GPIO `PB6` (`SCCB_SCL/SIOC`) і `PB7` (`SCCB_SDA/SIOD`). Апаратний `I2C1` для камери не використовується.

Для початкової інтеграції прийнято цільову частоту SCCB **до 100 kHz**. Оскільки це програмна реалізація GPIO, апаратного периферійного prescaler немає: частота визначається затримками між перемиканням `SCL` та виконанням операцій на `SDA`.

| Параметр                          | Значення                                     |
| --------------------------------- | -------------------------------------------- |
| Інтерфейс                         | SCCB                                         |
| Піни                              | `PB6/SIOC`, `PB7/SIOD`                       |
| Режим                             | Програмна реалізація через GPIO              |
| Цільова частота                   | До 100 kHz                                   |
| Номінальна тривалість періоду SCL | 10 µs                                        |
| Номінальна тривалість HIGH        | 5 µs                                         |
| Номінальна тривалість LOW         | 5 µs                                         |
| Апаратний prescaler               | Не застосовується                            |
| Метод формування затримок         | Програмний таймер затримки або `DWT->CYCCNT` |

Для `HCLK = 100 MHz` один цикл ядра триває:

$$
T_{HCLK}=\frac{1}{100\,000\,000}=10\ \text{ns}
$$

Номінальна затримка 5 µs відповідає:

$$
N=100\,000\,000\cdot5\cdot10^{-6}=500
$$

Отже, як початкове налаштування можна використовувати затримки приблизно по 500 циклів ядра на фазу HIGH і LOW. Реальна частота буде дещо нижчою через накладні витрати програмного коду; вона не повинна перевищувати встановлену цільову межу.

Під час програмної передачі SDA потрібно відпускати у фазах читання та перевіряти відповідь камери. Не слід трактувати SCCB як повністю взаємозамінний з I²C: для звітності необхідно окремо перевірити його відповідь на фазі, де стандартний I²C-декодер очікує ACK.

### 5.4. SPI2 — пам'ять W25Q64

W25Q64 підключено до апаратної периферії `SPI2` через `PB13/SCK`, `PB14/MISO` та `PB15/MOSI`. Сигнал вибору пам'яті `CS#` керується окремим GPIO `PB12`.

Для початкової інтеграції вибрано **SPI Mode 0** і частоту `SCK = 3.125 MHz`. Така частота нижча за максимальну частоту SPI W25Q64FV і водночас зручна для верифікації логічним аналізатором з частотою дискретизації близько 24 MS/s.

| Параметр                    | Значення                             |
| --------------------------- | ------------------------------------ |
| Периферія                   | `SPI2`                               |
| Піни                        | `PB13/SCK`, `PB14/MISO`, `PB15/MOSI` |
| Alternate Function          | `AF5`                                |
| Джерело тактування          | `PCLK1 = 50 MHz`                     |
| Режим SPI                   | Mode 0                               |
| `CPOL`                      | `0`                                  |
| `CPHA`                      | `0`                                  |
| Порядок бітів               | MSB first                            |
| Розмір кадру                | 8 біт                                |
| Prescaler `SPI_CR1.BR[2:0]` | `/16`, код `011`                     |
| Цільова частота `SCK`       | 3.125 MHz                            |
| Керування `CS#`             | Програмне, GPIO `PB12`               |

W25Q64FV підтримує стандартний SPI у Mode 0 і Mode 3. Для цього стенда вибрано Mode 0 (`CPOL = 0`, `CPHA = 0`), тому в стані очікування SCK перебуває на низькому рівні, а дані зчитуються відповідно до стандартної часової діаграми цього режиму. [[W25Q64FV datasheet, §7.2.34, pp. 61–62](https://www.pjrc.com/store/w25q64fv.pdf)]

#### 5.4.1. Розрахунок частоти SPI

У STM32F411 частота SPI формується діленням тактової частоти відповідної APB-шини:

$$
f_{SCK}=\frac{f_{PCLK1}}{D}
$$

Для прескалера `/16`:

$$
f_{SCK}=\frac{50\,000\,000}{16}
=3\,125\,000\ \text{Hz}
$$

Отже, цільова частота SCK становить **3.125 MHz**, а тривалість одного такту:

$$
T_{SCK}=\frac{1}{3\,125\,000}=320\ \text{ns}
$$

Для SPI-периферії F411 вибір prescaler здійснюється полями `BR[2:0]` регістра `SPI_CR1`. Керування CS# через GPIO дозволяє утримувати пам'ять вибраною протягом усієї команди та відповіді, не покладаючись на автоматичне перемикання апаратного NSS.

#### 5.4.2. Перевірка SPI

Під час початкової перевірки потрібно виконати команду `Read JEDEC ID` (`0x9F`) та зафіксувати її разом із трьома байтами відповіді `EF 40 17`. Сигнал `CS#` має залишатися низьким протягом усієї транзакції, включаючи передавання команди і читання ідентифікатора.

При частоті SCK 3.125 MHz рекомендується встановити частоту дискретизації логічного аналізатора не нижче 16 MS/s, а за наявності відповідного режиму — 24 MS/s або вище. Це дає приблизно 5–8 відліків на період SCK і забезпечує кращі умови для декодування коротких транзакцій.

### 5.5. USART1 — командний інтерфейс YP-05

YP-05 підключено до апаратного `USART1` через `PA9/TX` і `PA10/RX`. Ця периферія тактується від `PCLK2 = 100 MHz`. Для командного інтерфейсу прийнято стандартний формат **115200 baud, 8N1**.

| Параметр              | Значення            |
| --------------------- | ------------------- |
| Периферія             | `USART1`            |
| Піни                  | `PA9/TX`, `PA10/RX` |
| Alternate Function    | `AF7`               |
| Джерело тактування    | `PCLK2 = 100 MHz`   |
| Швидкість передавання | 115200 baud         |
| Довжина слова         | 8 біт               |
| Парність              | Вимкнена            |
| Stop bits             | 1                   |
| Oversampling          | 16                  |
| `USART_BRR`           | `0x0364`            |
| Hardware flow control | Вимкнений           |

USB-UART міст FT232RL підтримує швидкості передавання значно вищі за 115200 baud, тому вибране значення не створює обмеження для командного інтерфейсу. Джерело: [FT232R datasheet, UART Baud Rate Generator](https://ftdichip.com/wp-content/uploads/2020/08/DS_FT232R.pdf).

#### 5.5.1. Розрахунок BRR

Для oversampling by 16 використовується співвідношення:

$$
USARTDIV=\frac{f_{PCLK2}}{16\cdot Baud}
$$

Підставляємо `PCLK2 = 100 MHz` і `Baud = 115200`:

$$
USARTDIV=
\frac{100\,000\,000}{16\cdot115\,200}
\approx54.25347
$$

Після округлення дробової частини до найближчого доступного значення формується регістр:

```c
USART1->BRR = 0x0364;
```

Значення `0x0364` відповідає ефективному дільнику:

$$
D = 0\text{x}364 = 868
$$

Тоді фактична швидкість:

$$
Baud_{\text{actual}}=
\frac{100\,000\,000}{868}
\approx115\,207.37\ \text{baud}
$$

Відносна похибка:

$$
\varepsilon=
\frac{115\,207.37-115\,200}{115\,200}
\cdot100\%
\approx0.0064\%
$$

Ця похибка є малою для асинхронного UART-з'єднання з FT232RL.

### 5.6. TIM1 — формування XCLK для OV7670

Сигнал `XCLK` камери формується апаратним PWM на `PA8/TIM1_CH1`. Таймер `TIM1` тактується від APB2, а за прийнятого дільника APB2 `/1` отримує частоту 100 MHz.

Для початкової конфігурації встановлюється `XCLK = 10 MHz` із коефіцієнтом заповнення 50 %.

| Параметр                    | Значення            |
| --------------------------- | ------------------- |
| Таймер                      | `TIM1`              |
| Канал                       | `CH1`               |
| Вихідний пін                | `PA8`, `AF1`        |
| Джерело тактування          | `TIM1CLK = 100 MHz` |
| Режим                       | Edge-aligned PWM    |
| Prescaler `PSC`             | `0`                 |
| Auto-reload `ARR`           | `9`                 |
| Compare `CCR1`              | `5`                 |
| Розрахункова частота `XCLK` | 10 MHz              |
| Коефіцієнт заповнення       | 50 %                |

Для edge-aligned PWM частота на виході визначається формулою:

$$
f_{PWM}=
\frac{f_{TIM1}}
{(PSC+1)(ARR+1)}
$$

Після підстановки:

$$
f_{PWM}=
\frac{100\,000\,000}
{(0+1)(9+1)}
=10\,000\,000\ \text{Hz}
$$

Період сигналу дорівнює:

$$
T_{XCLK}=\frac{1}{10\,000\,000}=100\ \text{ns}
$$

За `CCR1 = 5` і періоду 10 тактів таймера сигнал має приблизно 50 % заповнення, тобто HIGH і LOW тривають по 50 ns. Режими та регістри таймерів описано в [RM0383, §13, TIMx; STM32F411 datasheet, Table 4, p. 28](https://www.st.com/resource/en/reference_manual/dm00119316.pdf).

Оскільки `TIM1` є таймером розширеного керування, під час запуску PWM необхідно також увімкнути вихід каналу та головний вихід таймера (MOE). Це потрібно для фактичної появи тактового сигналу на `PA8`.

Частота 10 MHz є початковим проєктним значенням `XCLK`, а не частотою `PCLK`. Зовнішній тактовий сигнал камери запускається до звернень SCCB, оскільки камера потребує тактування для штатної роботи регістрового інтерфейсу.

### 5.7. OV7670 — налаштування внутрішньої частоти та PCLK

`PCLK` є вихідним сигналом камери та підключений до `PC9/TIM3_CH4`. Частота PCLK не визначається prescaler STM32: вона залежить від вхідного `XCLK`, налаштування PLL/clock prescaler камери та режиму вихідного зображення.

Для першої конфігурації передбачається обмежити швидкість виходу даних до цільової частоти **не вище приблизно 1 MHz**, щоб зменшити навантаження на DMA та спростити перевірку часових співвідношень.

Згідно з [OV7670/OV7171 Implementation Guide, §3.2.1, Table 3-2 та Table 3-3, pp. 12–13](https://web.mit.edu/6.111/www/f2017/tools/OV7670app.pdf), внутрішня частота камери визначається виразом:

$$
f_{INT}=
\frac{f_{XCLK}\cdot PLL\_Multiplier}
{2\cdot(CLKRC[5:0]+1)}
$$

Для початкової оцінки, якщо застосовується множник PLL ×4 (`DBLV[7:6] = 01`) і `CLKRC[5:0] = 19` (`0x13`), при `XCLK = 10 MHz` отримуємо:

$$
f_{INT}=
\frac{10\,MHz\cdot4}{2\cdot(19+1)}
=1\,MHz
$$

Це значення задає розрахункову внутрішню частоту камери за наведеними параметрами. Воно не гарантує, що `PCLK` у будь-якому форматі виводу дорівнюватиме рівно 1 MHz: у режимах масштабованого зображення pixel clock також залежить від налаштувань масштабування та дільника PCLK. Фактичну частоту потрібно перевірити на `PC9` і скоригувати регістри камери за результатами вимірювання.

Під час першої перевірки рекомендується застосувати зменшений формат кадру, який не перевищує доступний обсяг SRAM після врахування витрат на DMA та інші дані прошивки. Повний необроблений VGA-кадр не можна безпосередньо розмістити в SRAM STM32F411RE без потокової обробки або зменшення даних: мікроконтролер має 128 КБ SRAM. [[STM32F411 datasheet, Figure 3, p. 16](https://www.st.com/resource/en/datasheet/stm32f411re.pdf)]

Для DVP важливо синхронізувати момент зчитування даних із фронтом PCLK. На першому етапі необхідно зафіксувати `PCLK`, `HREF` та `VSYNC` у PulseView, перевірити валідну ділянку рядка та обрати той фронт захоплення, на якому дані вже стабільні.

### 5.8. TIM3 та DMA1 — захоплення паралельних даних камери

`TIM3_CH4` використовується як вхід захоплення `PCLK` на `PC9`. Подія input capture формує DMA-запит, за яким контролер DMA читає `GPIOC->IDR` і переносить зразок у SRAM.

Це не є апаратним DCMI: STM32F411RE не має DCMI. Реалізація спирається на звичайний таймер, DMA та GPIO. Відповідність `TIM3_CH4` до DMA1 Stream 2 / Channel 5 наведена в [RM0383, Table 27, p. 171](https://www.st.com/resource/en/reference_manual/dm00119316.pdf).

| Параметр                 | Значення                                          |
| ------------------------ | ------------------------------------------------- |
| Вхідний сигнал           | `OV7670 PCLK`                                     |
| Вхідний пін              | `PC9/TIM3_CH4`, `AF2`                             |
| Джерело тактування TIM3  | `TIM3CLK = 100 MHz`                               |
| Prescaler таймера `PSC`  | `0`                                               |
| `ARR`                    | `0xFFFF`                                          |
| Режим каналу             | Input capture, захоплення одного вибраного фронту |
| Input capture prescaler  | DIV1                                              |
| Початковий input filter  | `0`, без цифрової фільтрації                      |
| Джерело DMA-запиту       | Подія `TIM3_CH4`                                  |
| DMA stream               | `DMA1 Stream 2`                                   |
| DMA channel              | `Channel 5`                                       |
| Адреса джерела даних     | `GPIOC->IDR`                                      |
| Напрямок DMA             | Peripheral-to-memory                              |
| Розмір елемента          | 32-бітний зразок порту в 32-бітному буфері        |
| Зміна адрес джерела      | Вимкнена                                          |
| Зміна адреси призначення | Увімкнена                                         |

Прийнято `PSC = 0`, тому лічильник TIM3 працює з частотою 100 MHz та має крок 10 ns. У режимі input capture частота самого таймера не визначає частоту PCLK; запит генерується кожною подією захоплення обраного фронту зовнішнього сигналу.

Оскільки камера виводить дані на восьми GPIO, кожне зчитування `GPIOC->IDR` зберігає одночасні рівні всіх восьми бітів DVP, навіть коли сигнали `D0...D7` розташовані на різних номерах бітів порту. У цьому документі DMA зберігає повний 32-бітний зразок, після чого програмне забезпечення виділяє біти `PC2...PC8` та `PC10`.

**Для роботи DMA необхідно активувати запит capture channel (`CC4DE`) і не активувати запит оновлення таймера (`UDE`).** У таблиці DMA request mapping `TIM3_CH4` та `TIM3_UP` мають спільний маршрут DMA1 Stream 2 / Channel 5. Одночасне використання обох джерел у цьому stream не передбачається; під час захоплення камери використовується лише `TIM3_CH4`.

Під час стартової перевірки слід обрати фронт захоплення відповідно до налаштувань камери. Наприклад, якщо `COM10[4] = 0` і камера оновлює дані на спадному фронті PCLK, зчитування GPIO доцільно запускати на наступному висхідному фронті. Це дає приблизно половину періоду PCLK між оновленням даних і запитом на читання. Правильність цього вибору потрібно підтвердити осцилограмою та тестовим кадром, оскільки затримка DMA та часові параметри реального модуля впливають на результат.

Для першого bring-up рекомендовано передбачити зменшений кадр, наприклад QQVGA у форматі Raw Bayer RGB. Кадр 160 × 120 містить 19200 зразків пікселя; за одного 32-бітного DMA-зразка на піксель буфер потребує:

$$
19200\cdot4=76800\ \text{байт}
$$

Це вкладається у 128 КБ SRAM STM32F411RE, але займає її значну частину. Для решти прошивки необхідно залишити місце під стек, структури журналу та інші буфери. Якщо використовується вихідний формат із двома байтами на піксель або більша роздільна здатність, слід переходити до потокового захоплення рядками/порціями, а не виділяти необмежений буфер кадру.

#### 5.8.1. Перевірка відсутності DMA-конфліктів

У вибраній схемі передбачено такі маршрути:

| Периферія   | Напрямок            | DMA-контролер | Stream | Channel | Примітка                                                      |
| ----------- | ------------------  | ------------- | -----: | ------: | ------------------------------------------------------------- |
| `TIM3_CH4`  | Зразок GPIO -> SRAM | DMA1          |      2 |       5 | Захоплення `PCLK`; не вмикати `TIM3_UP` DMA на цьому маршруті |
| `I2C1_RX`   | I²C -> SRAM         | DMA1          |      0 |       1 | Читання даних сенсорів                                        |
| `I2C1_TX`   | SRAM -> I²C         | DMA1          |      6 |       1 | Передавання команд/даних по I²C                               |
| `SPI2_RX`   | SPI -> SRAM         | DMA1          |      3 |       0 | Читання відповідей Flash                                      |

### 5.10. Перевірка параметрів логічним аналізатором

Під час інтеграції необхідно виміряти фактичні частоти шин і зіставити їх із розрахунками вище.

1. **I²C1:** записати транзакцію читання `WHO_AM_I` одного з сенсорів та багатобайтове читання. Виміряти період SCL; очікуване значення — приблизно 10 µs.
2. **SCCB:** записати читання `PID` і `VER` камери. Перевірити період SCL/SIOC та фазу відповіді SDA.
3. **SPI2:** записати команду `0x9F` і три байти JEDEC ID. Очікувана частота SCK — 3.125 MHz; перевірити, що CS# залишається низьким протягом транзакції.
4. **USART1:** захопити UART-повідомлення із початкової самоперевірки пристроїв та перевірити швидкість 115200 baud.
5. **XCLK:** перевірити частоту й коефіцієнт заповнення на PA8. Для виконання тесту періоду та ширини PWM принаймні для двох значень можна тимчасово, коли камера утримується в RESET/PWDN, перемкнути `TIM1_CH1` на діагностичні частоти 100 kHz (`PSC=0`, `ARR=999`, `CCR1=500`) та 200 kHz (`PSC=0`, `ARR=499`, `CCR1=250`). Ці значення використовуються лише для перевірки таймера і не є робочими частотами XCLK камери.
6. **DVP:** записати одночасно PCLK, HREF і VSYNC. Перевірити межі рядків і кадру, а також стабільність даних на вибраному фронті PCLK.

Для SPI доцільно застосовувати частоту дискретизації логічного аналізатора не нижче 16 MS/s, а для кращої якості декодування — 24 MS/s або більше. Для SCCB, I²C та UART достатньо меншої швидкості дискретизації, але значення мають забезпечувати кілька відліків на кожний період тактового сигналу. Якщо максимальна частота аналізатора не дозволяє надійно перевірити XCLK 10 MHz, його точну частоту та ширину імпульсу слід додатково перевірити осцилографом або аналізатором із вищою частотою дискретизації.

Стенд збирається без пайки через штатні роз'єми NUCLEO-F411RE. Усі зовнішні модулі підключаються одночасно. Позначення контактів `CN7` і `CN10` наведені відповідно до документації плати Nucleo [UM1724, Tables 16, 29](https://www.st.com/resource/en/user_manual/dm00105823.pdf).

### 6.2. Інструкція монтажу

1. **Знеструмити стенд.** Від'єднати USB від Nucleo та USB Type-C від YP-05 до завершення монтажу.
2. **Підключити GY-89.** З'єднати `SCL`, `SDA`, `VIN` та `GND` згідно з таблицею, яка наведена в пункті 6.1.1. Не підключати `3V3`, `SD0/SA0`, `CS1` і `CS2`.
3. **Підключити W25Q64.** З'єднати `CLK`, `D0`, `DI`, `CS`, `VCC` і `GND` згідно з таблицею, що наведена в пункті 6.1.2. Перевірити, що `CS` йде саме на `PB12`, а не на `PB13–PB15`.
4. **Підключити YP-05.** З'єднати `PA9 -> RXD`, `TXD -> PA10` і `GND -> GND`. Не з'єднувати `VCC` адаптера з живленням Nucleo. Після монтажу підключити адаптер до ПК через USB Type-C.
5. **Підключити OV7670.** Спочатку з'єднати SCCB, XCLK, RESET і PWDN, потім усі лінії `D0–D7`, `PCLK`, `HREF`, `VSYNC`, а після цього — живлення `3.3V` і `DGND`. Особливо уважно перевірити, що `PCLK` підключено до `PC9`, а `D7` — до `PC10`.
6. **Перевірити землю і живлення.** Переконатися, що всі модулі мають спільний GND зі STM32, `OV7670` і `W25Q64` отримують 3,3 В, а `GY-89` — 5 В на `VIN`.
7. **Перевірити штатні ресурси Nucleo.** Не підключати зовнішні модулі до `PA2/PA3`, `PA5`, `PC13`, `PA13/PA14`, оскільки вони залишені для ST-LINK VCP, LD2, кнопки користувача та SWD відповідно.
8. **Увімкнути живлення і виконати самоперевірку.** Перевірити ID-регістри трьох вузлів GY-89, PID/VER камери та JEDEC ID пам'яті. До запуску повного захоплення кадру переконатися, що XCLK присутній, SCCB відповідає на запити, а на PCLK/HREF/VSYNC є очікувані сигнали.

Після складання всі фактичні з'єднання мають бути звірені зі зведеною таблицею в розділі 2.

## 7. Відхилені варіанти

Під час проєктування pinout розглядалися альтернативні варіанти призначення контактів і периферійних блоків STM32F411RE. Остаточний вибір визначався не лише доступністю окремих пінів, а й необхідністю одночасної роботи всіх модулів, збереження штатних ресурсів Nucleo та уникнення конфліктів DMA.

Нижче наведено чотири варіанти, від яких ми відмовилися під час формування поточної розкладки.

### 7.1. Підключення GY-89 до I²C1 на PB6/PB7

**Альтернативний варіант.** Використати `PB6` як `I2C1_SCL`, а `PB7` як `I2C1_SDA` замість поточної пари `PB8/PB9`. Обидві пари підтримують відповідні альтернативні функції I²C1 у STM32F411RE. [[STM32F411 datasheet, Table 9](https://www.st.com/resource/en/datasheet/stm32f411re.pdf)]

**Причина відмови.** У прийнятій конфігурації `PB6/PB7` уже призначені для програмно реалізованого інтерфейсу SCCB камери OV7670. Одночасне використання тих самих фізичних контактів для `I2C1` та SCCB спричинило б конфлікт пінів: обидва інтерфейси керували б спільними лініями, що унеможливило б незалежне звернення до сенсорів і камери.

Перенесення SCCB на іншу пару GPIO теоретично дозволило б використати цей варіант, але вимагало б зміни вже погодженої розкладки камери та повторної перевірки всіх з'єднань. Практичної переваги порівняно з поточним рішенням це не дає.

Тому залишено `PB8/PB9`: ця пара підтримує `I2C1_SCL/I2C1_SDA`, відповідає штатним контактам Arduino `D15/D14` на NUCLEO-F411RE та не займає GPIO, виділені під SCCB і паралельну шину камери. [[UM1724, Table 16, p. 44; Table 29, p. 59](https://www.st.com/resource/en/user_manual/dm00105823.pdf)]

### 7.2. Підключення W25Q64 до SPI1 на PA5/PA6/PA7

**Альтернативний варіант.** Підключити пам'ять W25Q64 до штатної Arduino SPI-пари Nucleo: `PA5/SPI1_SCK`, `PA6/SPI1_MISO` та `PA7/SPI1_MOSI`. Для `CS#` можна було б використати окремий GPIO.

**Причина відмови.** На NUCLEO-F411RE контакт `PA5` одночасно підключений до вбудованого світлодіода користувача `LD2` через штатну обв'язку плати. Це підтверджено документацією Nucleo: сигнал Arduino `D13` відповідає `PA5/SPI1_SCK`, а перемичка `SB21` з'єднує `LD2` із цим сигналом. [[UM1724, Table 16, p. 44; Table 10, §7.11, p. 27](https://www.st.com/resource/en/user_manual/dm00105823.pdf)]

Оскільки світлодіод `LD2` використовується у проєкті для індикації станів `DISARMED`, `ARMED` та інцидентів, використання `PA5` як тактової лінії SPI призвело б до несумісності двох призначень. Під час передавання даних на `SCK` перемикання сигналу могло б впливати на світлодіод, а LED-індикація перестала б виконувати свою функцію належним чином.

Від'єднання `LD2` через зміну solder bridge дозволило б звільнити `PA5`, але позбавило б команду штатного світлодіода або вимагало б його перенесення на інший GPIO, що спричинило б додаткові зміни в документації та прошивці.

Тому обрано `SPI2` на `PB13/PB14/PB15`, а `CS#` винесено на `PB12`. Це дозволяє зберегти `PA5/LD2` для індикації та уникнути зміни штатної конфігурації Nucleo. [[STM32F411 datasheet, Table 9](https://www.st.com/resource/en/datasheet/stm32f411re.pdf)]

### 7.3. Підключення YP-05 до USART2 на PA2/PA3

**Альтернативний варіант.** Використати `PA2/USART2_TX` та `PA3/USART2_RX` для підключення YP-05 замість обраної пари `PA9/PA10` периферії USART1.

**Причина відмови.** У штатній конфігурації NUCLEO-F411RE контакти `PA2/PA3` використовуються для зв'язку між мікроконтролером і вбудованим ST-LINK/V2-1, який надає віртуальний COM-порт (ST-LINK VCP). З'єднання реалізоване через відповідні solder bridges плати. [[UM1724, §7.10, p. 26; Table 10, §7.11, p. 27](https://www.st.com/resource/en/user_manual/dm00105823.pdf)]

Підключення YP-05 до цієї самої пари без зміни штатної маршрутизації спричинило б дублювання UART-з'єднання. Зокрема, вихід `TXD` зовнішнього адаптера та вихід передавання даних ST-LINK могли б одночасно бути підключені до `PA3/USART2_RX`. Це створює ризик конфлікту вихідних сигналів, а також ускладнює незалежне використання штатного `monitor` і зовнішнього командного інтерфейсу.

Відключення штатного з'єднання ST-LINK через solder bridges могло б усунути цей конфлікт, але позбавило б команду звичного каналу моніторингу або вимагало б додаткової зміни конфігурації плати.

Тому для YP-05 обрано `USART1` на `PA9/PA10` (`AF7`), а `USART2` на `PA2/PA3` збережено для штатного ST-LINK VCP. Обидва UART-інтерфейси можуть використовуватися незалежно без зміни solder bridges Nucleo.

### 7.4. Перенесення PCLK камери на PA6/TIM3_CH1

**Альтернативний варіант.** Підключити вихід `PCLK` камери OV7670 до `PA6`, який підтримує `TIM3_CH1` у режимі альтернативної функції `AF2`, замість поточного `PC9/TIM3_CH4`. При цьому вісім ліній даних камери залишилися б на `GPIOC`.

**Причина відмови.** Основне обмеження цього варіанта пов'язане з маршрутизацією DMA, а не лише з доступністю піна. Згідно з таблицею DMA request mapping для STM32F411, запит `TIM3_CH1` маршрутизується до **DMA1 Stream 4 / Channel 5**, тоді як передавання даних із пам'яті до `SPI2` (`SPI2_TX`) використовує **DMA1 Stream 4 / Channel 0**. [[RM0383, Table 27, p. 171](https://www.st.com/resource/en/reference_manual/dm00119316.pdf)]

Хоча значення `Channel` різні, обидві периферійні функції потребують одного й того самого DMA stream. Кожен stream може бути налаштований лише на один канал вибору запиту одночасно, тому під час паралельної роботи захоплення камери та передавання команд до Flash виник би конфлікт DMA-маршрутизації.

У поточній конфігурації `PCLK` підключений до `PC9/TIM3_CH4`, для якого запит DMA маршрутизується до **DMA1 Stream 2 / Channel 5**. Це дозволяє залишити `DMA1 Stream 4 / Channel 0` доступним для `SPI2_TX` і не створювати конфлікту між захопленням камери та доступом до SPI Flash.

Тому остаточно залишено `PC9/TIM3_CH4` як вхід `PCLK`, оскільки ця розкладка забезпечує потрібний маршрут DMA та сумісність із запланованими операціями `SPI2`.
